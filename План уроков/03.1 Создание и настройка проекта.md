# Настройка чистой архитектуры с нуля

Пошаговый урок: от пустой папки до готовой структуры .NET 10 решения.
В конце у тебя будет шаблон, который мы будем использовать для всех
последующих микросервисов.

## Точка старта

- **Установлен .NET 10 SDK** — проверь: `dotnet --version` должен вернуть `10.x.xxx`.
- **Терминал** — на Mac/Linux встроен, на Windows используй Windows Terminal или Git Bash.
- **Установлен Git** — проверь: `git --version`. Понадобится с первого же шага.
- **Базовые знания C#** — знаешь, что такое класс, интерфейс, пространство имён.

Ни Visual Studio, ни JetBrains не нужны — делаем всё через CLI.
Потом можно открыть в IDE.

## Что такое чистая архитектура

Чистая архитектура — это способ организации кода, при котором бизнес-логика
не зависит от фреймворков, баз данных и HTTP. Всё строится по принципу лука:
в центре — чистая логика, снаружи — детали реализации.

**Правило одно:** зависимости идут только внутрь. `Web` знает про `Core`,
`Core` знает про `Domain`, но `Domain` ничего не знает про HTTP или Postgres.

### Слои нашего решения

| Слой               | Проект                                    | Что хранится                              |
| ------------------ | ----------------------------------------- | ----------------------------------------- |
| Contracts          | `TemplateService.Contracts`               | DTO-классы: Request/Response для HTTP     |
| Domain             | `TemplateService.Domain`                  | Сущности, value objects, бизнес-правила   |
| Core (Application) | `TemplateService.Core`                    | Use cases, обработчики команд/запросов    |
| Infrastructure     | `TemplateService.Infrastructure.Postgres` | DbContext, репозитории, миграции          |
| Web (API)          | `TemplateService.Web`                     | `Program.cs`, конфигурация HTTP-пайплайна |

### Направление зависимостей

```text
TemplateService.Web
      ↓
TemplateService.Core  ←  TemplateService.Infrastructure.Postgres
      ↓                           ↓
TemplateService.Domain          TemplateService.Domain
```

`TemplateService.Core` также ссылается на `TemplateService.Contracts` — DTO-классы запросов и ответов.

`Domain` — самый внутренний слой. Он ничего не знает про базу данных или HTTP.
`Web` — самый внешний; он всё собирает вместе, но сам ничего не реализует.

## Шаг 1. Создаём папки, решение и закрепляем SDK

### Создаём корневую папку и solution

```bash
mkdir template-service && cd template-service
mkdir -p backend/TemplateService/src
cd backend/TemplateService
dotnet new sln -n TemplateService
```

После этого в `backend/TemplateService/` появится файл `TemplateService.slnx`.

> **Почему `.slnx`, а не `.sln`?** `.slnx` — XML-формат solution-файла из .NET 9. Он чище читается, реже даёт конфликты в git и поддерживается всеми актуальными IDE. Старый `.sln` — текстовый формат, который сложно читать вручную.
>
> **Про структуру решений.** Каждый микросервис живёт в своей папке и имеет собственный `.slnx` для изолированной разработки. Когда сервисов станет несколько, можно добавить общий `backend/backend.slnx`, включающий все сервисы — удобно открывать весь бэкенд в IDE одним действием. Пока у нас один сервис — одного `TemplateService.slnx` достаточно.

### Инициализируем Git

```bash
# из папки template-service/
cd ../..
git init
```

### Закрепляем версию SDK (global.json)

`global.json` гарантирует, что все в команде используют одну и ту же версию .NET SDK. Создать файл **в корне репозитория** (`template-service/`):

```bash
dotnet new globaljson --sdk-version 10.0.203 --roll-forward latestFeature
```

`rollForward: latestFeature` — если установлена более новая patch-версия (10.0.2xx), SDK возьмёт её автоматически.

### Добавляем .gitignore

```bash
dotnet new gitignore
```

Команда создаёт стандартный `.gitignore` для .NET — исключает `bin/`, `obj/`, `.vs/` и артефакты сборки.

### Первый коммит

```bash
git add .gitignore global.json
git commit -m "chore: init repo with gitignore and global.json"
```

## Шаг 2. Создаём пять проектов

Все команды выполнять из папки `backend/TemplateService/`.

```bash
# Contracts — только DTO-записи, без бизнес-логики
dotnet new classlib -n TemplateService.Contracts -o src/TemplateService.Contracts

# Domain — сущности и бизнес-правила

# Infrastructure — база данных
dotnet new classlib -n TemplateService.Infrastructure.Postgres -o src/TemplateService.Infrastructure.Postgres

# Web — HTTP-слой, Program.cs
dotnet new web -n TemplateService.Web -o src/TemplateService.Web
```

```bash
dotnet sln TemplateService.slnx add \
  src/TemplateService.Contracts/TemplateService.Contracts.csproj \
  src/TemplateService.Domain/TemplateService.Domain.csproj \
  src/TemplateService.Core/TemplateService.Core.csproj \
  src/TemplateService.Infrastructure.Postgres/TemplateService.Infrastructure.Postgres.csproj \
  src/TemplateService.Web/TemplateService.Web.csproj
```

Проверить, что все проекты в solution:

```bash
dotnet sln TemplateService.slnx list
```

Ожидаемый вывод — пять строк с путями к `.csproj`.

### Убираем лишние файлы

`dotnet new classlib` создаёт `Class1.cs` в каждом проекте — он нам не нужен:

```bash
Get-ChildItem -Path "src" -Recurse -Filter "Class1.cs" | Remove-Item -Force
```

> TemplateService.Contracts
> TemplateService.Core
    - TemplateService.Contracts
    - TemplateService.Domain
> TemplateService.Domain
> TemplateService.Infrastructure.Postgres
    - TemplateService.Core
> TemplateService.Web
    - TemplateService.Contracts
    - TemplateService.Core
    - TemplateService.Domain
    - TemplateService.Infrastructure.Postgres

## Шаг 3. Подключаем анализаторы (Directory.Build.props)

> Шаги 3–5 создают файлы конфигурации в `backend/`. Перейди туда: `cd ..` (если сейчас в `backend/TemplateService/`).

`Directory.Build.props` — файл, который MSBuild автоматически применяет ко **всем** проектам в папке `backend/` и вложенных папках. Не нужно дублировать настройки в каждом `.csproj`.

Создать файл `backend/Directory.Build.props`:

```xml
<Project>
  <!-- Общие настройки для ВСЕХ проектов -->
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>

    <!-- Все предупреждения становятся ошибками компиляции -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <CodeAnalysisTreatWarningsAsErrors>true</CodeAnalysisTreatWarningsAsErrors>

    <!-- Включаем стилевые правила в build -->
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <AnalysisLevel>latest</AnalysisLevel>
    <AnalysisMode>All</AnalysisMode>
    <EnableNETAnalyzers>true</EnableNETAnalyzers>

    <!-- Исключаем bin/obj из сборки -->
    <DefaultItemExcludes>$(DefaultItemExcludes);**/bin/**;**/obj/**</DefaultItemExcludes>
  </PropertyGroup>

  <!-- Анализаторы кода — применяются ко всем проектам автоматически -->
  <ItemGroup>
    <!-- Общие правила рефакторинга и стиля -->
    <PackageReference Include="Roslynator.Analyzers">
      <PrivateAssets>all</PrivateAssets>
      <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
    </PackageReference>

    <!-- Правила безопасности и корректности -->
    <PackageReference Include="Meziantou.Analyzer">
      <PrivateAssets>all</PrivateAssets>
      <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
    </PackageReference>

    <!-- Правила для async/await -->
    <PackageReference Include="AsyncFixer">
      <PrivateAssets>all</PrivateAssets>
      <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
    </PackageReference>

    <!-- Правила Sonar — безопасность и качество кода -->
    <PackageReference Include="SonarAnalyzer.CSharp">
      <PrivateAssets>all</PrivateAssets>
      <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
    </PackageReference>
  </ItemGroup>

</Project>
```

**Ключевые моменты:**

- `TreatWarningsAsErrors=true` — предупреждения анализаторов ломают сборку. Это неудобно поначалу, но защищает от накопления технического долга.
- `PrivateAssets=all` + `IncludeAssets=...analyzers...` — анализатор не попадает в зависимости сервиса, он нужен только во время сборки.
- Версии пакетов не указаны здесь — они живут в `Directory.Packages.props` (следующий шаг).

## Шаг 4. Центральное управление версиями пакетов (Directory.Packages.props)

Без этого файла у тебя 5 проектов, каждый из которых может указывать разные версии одного и того же пакета. Со временем версии расходятся, возникают конфликты.

`Directory.Packages.props` решает это: версии пакетов указываются в **одном месте**, а в `.csproj` пишется только имя пакета без версии.

Создать файл `backend/Directory.Packages.props`:

```xml
<Project>
  <PropertyGroup>
    <!-- Включаем центральное управление версиями -->
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <!-- Транзитивные зависимости тоже закрепляются -->
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

  <ItemGroup>
    <!-- Паттерн Result<T, Error> для бизнес-ошибок -->
    <PackageVersion Include="CSharpFunctionalExtensions" Version="3.6.0" />

    <!-- База данных -->
    <PackageVersion Include="Microsoft.EntityFrameworkCore" Version="10.0.7" />
    <PackageVersion Include="Microsoft.EntityFrameworkCore.Design" Version="10.0.7" />
    <PackageVersion Include="Npgsql.EntityFrameworkCore.PostgreSQL" Version="10.0.0" />
    <PackageVersion Include="Dapper" Version="2.1.66" />

    <!-- Валидация и авторегистрация DI -->
    <PackageVersion Include="FluentValidation" Version="12.1.1" />
    <PackageVersion Include="FluentValidation.DependencyInjectionExtensions" Version="12.1.1" />
    <PackageVersion Include="Scrutor" Version="7.0.0" />

    <!-- HTTP / OpenAPI -->
    <PackageVersion Include="Microsoft.AspNetCore.OpenApi" Version="10.0.7" />
    <PackageVersion Include="Scalar.AspNetCore" Version="2.13.0" />

    <!-- Health checks -->
    <PackageVersion Include="Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore" Version="10.0.7" />

    <!-- Анализаторы (версии здесь, подключение в Directory.Build.props) -->
    <PackageVersion Include="Roslynator.Analyzers" Version="4.15.0" />
    <PackageVersion Include="Meziantou.Analyzer" Version="3.0.44" />
    <PackageVersion Include="AsyncFixer" Version="2.1.0" />
    <PackageVersion Include="SonarAnalyzer.CSharp" Version="10.24.0.138807" />
  </ItemGroup>
</Project>
```

Теперь в каждом `.csproj` пакеты подключаются **без версии**:

```xml
<!-- Пример: в TemplateService.Infrastructure.Postgres.csproj — только имя, без версии -->
<PackageReference Include="Npgsql.EntityFrameworkCore.PostgreSQL" />
```

Версия будет взята из `Directory.Packages.props`. Чтобы обновить пакет — меняешь версию в одном файле.

## Шаг 5. Настройка анализаторов (.globalconfig)

### .globalconfig — глобальный приоритет над .editorconfig

`.globalconfig` позволяет отключать конкретные правила анализаторов с объяснением причины. Это важно: когда через год смотришь на `severity = none`, ты знаешь зачем.

Создать файл `backend/.globalconfig`:

```editorconfig
is_global = true

# Все правила категории security — ошибки
dotnet_analyzer_diagnostic.category-security.severity = error

# CA2007: ConfigureAwait — не нужен в ASP.NET Core (фреймворк сам управляет контекстом)
dotnet_diagnostic.CA2007.severity = none

# CA1062: проверка null-аргументов — nullable reference types делают это за нас
dotnet_diagnostic.CA1062.severity = none

# CA1812: не инстанцированные классы — ложные срабатывания на DI-классах
dotnet_diagnostic.CA1812.severity = none

# CA1034: вложенные типы — в vertical slice один файл содержит несколько типов (Command/Handler)
dotnet_diagnostic.CA1034.severity = none

# MA0004: ConfigureAwait — не нужен в ASP.NET Core
dotnet_diagnostic.MA0004.severity = none

# MA0048: имя файла = имя типа — конфликт с vertical slice (несколько типов в файле)
dotnet_diagnostic.MA0048.severity = none

# MA0051: длина метода — обработчики use case намеренно длинные
dotnet_diagnostic.MA0051.severity = none

# MA0053: sealed классы — слишком агрессивно для DDD-сущностей
dotnet_diagnostic.MA0053.severity = none

# RCS1090: ConfigureAwait — не нужен в ASP.NET Core
dotnet_diagnostic.RCS1090.severity = none

# AsyncFixer01: убрать async/await — меняет поведение исключений в middleware
dotnet_diagnostic.AsyncFixer01.severity = none

# S1135: TODO/FIXME комментарии — маяки, не баги
dotnet_diagnostic.S1135.severity = none

# S1144: неиспользуемые private члены — ложные срабатывания на EF shadow props
dotnet_diagnostic.S1144.severity = none

# Правила строже, чем по умолчанию:
dotnet_diagnostic.S1125.severity = error  # Redundant Boolean literal
dotnet_diagnostic.S6673.severity = error  # Serilog template placeholder order
dotnet_diagnostic.S108.severity  = error  # Пустой catch-блок без комментария
```

## Шаг 6. Настраиваем связи между проектами

Каждый слой ссылается только на те слои, которые лежат глубже. Ссылки добавляются через `<ProjectReference>` в `.csproj`.

### TemplateService.Contracts.csproj

Нет ссылок — только чистые DTO. Заменить содержимое файла `TemplateService/src/TemplateService.Contracts/TemplateService.Contracts.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
</Project>
```

### TemplateService.Domain.csproj

Ссылок на другие проекты нет — Domain самый внутренний слой. Добавляем только пакет для паттерна `Result<T, Error>`. Заменить содержимое `TemplateService/src/TemplateService.Domain/TemplateService.Domain.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <ItemGroup>
    <PackageReference Include="CSharpFunctionalExtensions" />
  </ItemGroup>
</Project>
```

### TemplateService.Core.csproj

Core знает про Domain и Contracts. Здесь будут жить use cases, валидаторы и обработчики. Заменить содержимое `TemplateService/src/TemplateService.Core/TemplateService.Core.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <ItemGroup>
    <ProjectReference Include="../TemplateService.Contracts/TemplateService.Contracts.csproj" />
    <ProjectReference Include="../TemplateService.Domain/TemplateService.Domain.csproj" />
  </ItemGroup>

  <ItemGroup>
    <PackageReference Include="FluentValidation" />
    <PackageReference Include="FluentValidation.DependencyInjectionExtensions" />
    <PackageReference Include="Scrutor" />
  </ItemGroup>
</Project>
```

### TemplateService.Infrastructure.Postgres.csproj

Infrastructure знает про Core и Domain. Здесь DbContext и репозитории. Заменить содержимое `TemplateService/src/TemplateService.Infrastructure.Postgres/TemplateService.Infrastructure.Postgres.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <ItemGroup>
    <ProjectReference Include="../TemplateService.Core/TemplateService.Core.csproj" />
    <ProjectReference Include="../TemplateService.Domain/TemplateService.Domain.csproj" />
  </ItemGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore" />
    <PackageReference Include="Microsoft.EntityFrameworkCore.Design" />
    <PackageReference Include="Npgsql.EntityFrameworkCore.PostgreSQL" />
    <PackageReference Include="Dapper" />
  </ItemGroup>
</Project>
```

### TemplateService.Web.csproj

Web знает про всё — он собирает приложение воедино. Заменить содержимое `TemplateService/src/TemplateService.Web/TemplateService.Web.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <ItemGroup>
    <ProjectReference Include="../TemplateService.Core/TemplateService.Core.csproj" />
    <ProjectReference Include="../TemplateService.Domain/TemplateService.Domain.csproj" />
    <ProjectReference Include="../TemplateService.Infrastructure.Postgres/TemplateService.Infrastructure.Postgres.csproj" />

    <PackageReference Include="Scalar.AspNetCore" />
    <PackageReference Include="Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore" />
  </ItemGroup>
</Project>
```

## Шаг 7. Что живёт в каждом слое

Структура создана. Теперь кратко о том, что мы будем писать в каждом проекте в следующих уроках.

### TemplateService.Contracts — только DTO

Записи (records) для запросов и ответов HTTP. Никакой логики.

```csharp
// Features/ServiceOrders/ServiceOrderContracts.cs
namespace TemplateService.Contracts.ServiceOrders;

public record CreateServiceOrderRequest(
    string CarNumber,
    string Description,
    Guid ClientId);

public record ServiceOrderResponse(
    Guid Id,
    string CarNumber,
    string Status,
    DateTimeOffset CreatedAt);
```

### TemplateService.Domain — бизнес-правила

Сущности, value objects, ошибки. Нет зависимости от HTTP или БД.

```csharp
// ServiceOrders/ServiceOrder.cs
namespace TemplateService.Domain.ServiceOrders;

public class ServiceOrder
{
    public Guid Id { get; private set; }
    public string CarNumber { get; private set; }
    public ServiceOrderStatus Status { get; private set; }
    public DateTimeOffset CreatedAt { get; private set; }

    public ServiceOrder(Guid id, string carNumber)
    {
        Id = id;
        CarNumber = carNumber;
        Status = ServiceOrderStatus.New;
        CreatedAt = DateTimeOffset.UtcNow;
    }
}

public enum ServiceOrderStatus { New, InProgress, Completed }
```

### TemplateService.Core — use cases

Один use case = один файл. Файл содержит: Command/Query, Endpoint, Validator, Handler.

```text
Core/
└── Features/
    └── ServiceOrders/
        ├── UseCases/
        │   └── CreateServiceOrder.cs   ← Command + Handler + Validator + Endpoint
        └── Queries/
            └── GetServiceOrderById.cs  ← Query + Handler + Endpoint
```

### TemplateService.Infrastructure.Postgres — доступ к данным

DbContext, конфигурации таблиц (EF Fluent API), репозитории, миграции.

```text
Infrastructure.Postgres/
├── TemplateServiceDbContext.cs
├── Configurations/
│   └── ServiceOrderConfiguration.cs
├── Repositories/
│   └── ServiceOrderRepository.cs
└── Migrations/
```

### TemplateService.Web — точка входа

`Program.cs` + методы-расширения для DI и HTTP-пайплайна. Никакой бизнес-логики.

```csharp
// Program.cs — итоговый вид (добавим в следующих уроках)
WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
builder.Services.AddCore();
builder.Services.AddInfrastructure(builder.Configuration, builder.Environment);
builder.AddPresentation();

WebApplication app = builder.Build();
app.UsePresentation();
await app.RunAsync();
```

Сейчас `AddCore()`, `AddInfrastructure()` и `AddPresentation()` ещё не существуют — мы добавим их в следующих уроках. Пока настроим рабочий `Program.cs` с Scalar.

## Шаг 8. Scalar — документация API и первые endpoints

### Почему не Swagger

До .NET 9 стандартом была библиотека **Swashbuckle** (`Swashbuckle.AspNetCore`) + Swagger UI. С выходом .NET 9 ситуация изменилась:

- Microsoft добавил **встроенную** поддержку OpenAPI через `Microsoft.AspNetCore.OpenApi` — это нативный генератор spec-файла.
- Swashbuckle официально не поддерживает .NET 9 и 10 (остался community-maintained).
- **Scalar** — современный UI поверх нативного OpenAPI-эндпоинта. Мы уже добавили оба пакета в `TemplateService.Web.csproj` на шаге 6.

### Обновляем Program.cs

`dotnet new web` создал минимальный `Program.cs`. Заменить его содержимое:

```csharp
WebApplicationBuilder builder = WebApplication.CreateBuilder(args);

// Нативный OpenAPI .NET 9/10
builder.Services.AddOpenApi();

// Для тестового контроллера
builder.Services.AddControllers();

WebApplication app = builder.Build();

// Minimal API endpoints
app.MapGet("/", () => "TemplateService is running!");

app.MapGet("/health", () => Results.Ok(new
{
    status = "healthy",
    timestamp = DateTimeOffset.UtcNow
}));

// MVC контроллеры
app.MapControllers();

if (!app.Environment.IsProduction())
{
    app.MapOpenApi();              // /openapi/v1.json
    app.MapScalarApiReference();   // /scalar/v1
}

await app.RunAsync();
```

### Тестовый контроллер

Создать файл `src/TemplateService.Web/Controllers/TestController.cs` (из папки `backend/TemplateService/`):

```csharp
using Microsoft.AspNetCore.Mvc;

namespace TemplateService.Web.Controllers;

[ApiController]
[Route("api/[controller]")]
public class TestController : ControllerBase
{
    [HttpGet]
    public IActionResult Get() =>
        Ok(new { message = "TestController works!", time = DateTimeOffset.UtcNow });

    [HttpGet("{id:int}")]
    public IActionResult GetById(int id) =>
        Ok(new { id, message = $"Item {id} found" });
}
```

### Типичные проблемы

**`error NETSDK1138`** — версия SDK не совпадает с `global.json`.
Проверь установленные SDK: `dotnet --list-sdks`.

**`error NU1604`** — пакет не найден в `Directory.Packages.props`.
Добавь `<PackageVersion Include="..." Version="..." />`.
