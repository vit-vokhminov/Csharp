Задание
Нужно спроектировать публичный API для трёх сущностей — Location, Department, Position — так, чтобы по нему фронтенд мог писать клиент параллельно с бэком.

В этой задаче нет ни бизнес-логики, ни хранения, ни валидации, ни Result-паттерна — это всё придёт в следующих задачах. Цель спроектировать REST-контракт и аккуратно разложить DTO по слоям. Реализация прицепится позже.

Scalar в проекте уже настроен — после запуска можно увидеть endpoint'ы прямо в нём.

Что нужно сделать
REST-API для трёх сущностей — спроектируй endpoint-ы для Location, Department, Position: создание, получение по id, получение списка, обновление, удаление. URL-схема, имена методов и коды ответов — по правилам REST (POST /locations, GET /locations/{id} и т.д.). Глядя на URL и метод, фронтендщик должен понимать, что endpoint делает, без чтения кода.

Контракты (DTO) — в отдельном проекте Contracts. На каждую сущность отдельные DTO под запрос на создание / обновление и под ответ. Адрес у локации — вложенный DTO, не плоский набор полей. Имена осмысленные (CreateLocationRequest, LocationResponse).

Один контроллер на сущность, без бизнес-логики — внутри action-а никакой реальной работы: возвращай заглушку (new Guid() для id, пустой массив для списка, 404 NotFound для несуществующих — на твой выбор). Цель шага — собрать публичный API и проверить, что Scalar его видит. Реализация прицепится позже.

Чистая граница слоёв — контроллер ничего не знает о Domain и Infrastructure. Если рука потянулась импортнуть доменную сущность прямо в action, чтобы «отдать как есть» — это сигнал, что контракт не описан. DTO из Contracts — единственное, чем контроллер общается с внешним миром.

Что должно быть готово
В проекте Contracts лежат DTO для всех трёх сущностей: запрос на создание, запрос на обновление, ответ. Адрес — вложенный DTO
Три контроллера — Locations, Departments, Positions, у каждого набор endpoint-ов по правилам REST
Контроллер ссылается только на Contracts — в сигнатурах action-ов нет ни одной доменной сущности и ни одного типа из EF Core
Между Domain и Contracts нет общих типов: даже если поля одинаковые, это разные классы
Запуск сервиса — Scalar показывает все endpoint-ы с типизированными request / response
POST с валидным JSON возвращает 200 / 201 с заглушкой; GET возвращает пустой список или 404 — ответы осмысленные по REST, не «200 со строкой ok»
