### Практический пример: сеть автозаправочных станций (АЗС)

Представь федеральную сеть АЗС «FuelFlow»: у неё есть региональные офисы, филиалы в городах, сами станции и мобильные бригады. Directory Service здесь — это единый источник правды об оргструктуре: кто где работает, какие роли есть в каждом подразделении, где физически расположены объекты.

---

<p></p>

### Как в этом примере работают три ключевых понятия

- **Подразделения (Department)** — иерархия управления: «Регион Центр» → «Филиал Москва» → «АЗС №12» → «Мобильная бригада №3».

- **Локации (Location)** — физические места: города, адреса станций, координаты мобильных точек. Одна АЗС может быть связана с несколькими локациями (основной адрес + резервная площадка для техники).

- **Должности (Position)** — роли: «Оператор АЗС», «Старший смены», «Инженер по оборудованию», «Менеджер филиала». В разных подразделениях могут быть одни и те же должности, но с разными зонами ответственности.

## Пример данных в доменной модели

### Подразделения (Department)

| id | name | slug | parentId | path |
|-------|-----|-------|-------|-------|
| d1 | Регион Центр | central-region | null | central-region |
| d2 | Филиал Москва | moscow-branch | d1 | central-region/moscow-branch |
| d3 | АЗС №12 | station-12 | d2 | central-region/moscow-branch/station-12 |
| d4 | Мобильная бригада №3 | mobile-team-3 | d3 | central-region/moscow-branch/station-12/mobile-team-3 |


**Зачем нужен path:** \
Фронтенд по пути `central-region/moscow-branch/station-12` сразу строит breadcrumbs: «Регион Центр / Филиал Москва / АЗС №12». API может быстро искать все подразделения ветки через префикс пути (в PostgreSQL это эффективно с индексом по `path`).

### Связи многие‑ко‑многим

**DepartmentLocation**

| id | departmentId | locationId | isPrimary | 
|-------|-----|-----|-----|
| dl1 | d3 (АЗС №12) | l2 (основная) | true |
| dl2 | d3 (АЗС №12) | l3 (резерв) | false |

`isPrimary = true` говорит, что это основная локация подразделения — её показывают в UI как «адрес подразделения», используют для маршрутизации заявок и т. п.

**DepartmentPosition**

| id | departmentId | positionId |
|-------|-----|-----|
| dp1 | d3 (АЗС №12) | p1 (Оператор АЗС) |
| dp2 | d3 (АЗС №12) | p2 (Старший смены) |
| dp3 | d4 (Мобильная бригада) | p3 (Инженер по оборудованию) |

#### Где домен защищает бизнес‑правила (на примерах из этого кейса)

- **Нельзя создать подразделение с пустым** `name` или некорректным `slug`
Например, `slug = "АЗС №12"` отклоняется на уровне домена: в `slug` разрешены только латинские буквы, цифры, дефисы и подчёркивания. Это гарантирует, что URL‑сегменты всегда валидны.

- **Путь (path) строится по единому правилу** \
Для дочернего подразделения путь всегда вычисляется как `parent.path + "/" + self.slug`. Нельзя вручную задать случайный путь. Если родитель переименовывают, путь дочерних подразделений автоматически становится невалидным при попытке сохранить изменения — это заставляет явно пересчитать пути в транзакции.

- **Нельзя связать подразделение с несуществующей локацией или должностью** \
В соединительных сущностях `DepartmentLocation` и `DepartmentPosition` хранятся только `id` сторон. Домен проверяет, что оба `id` существуют и принадлежат корректным типам. Это предотвращает «битые» связи, которые потом сложно чинить в БД и API.

- **Родительская ссылка защищена** \
`parentId` не может указывать на само подразделение (запрет циклов) и не может быть `id` сущности другого типа. Корневое подразделение имеет `parentId = null`, это тоже часть инварианта.

- **Локация подразделения может быть только одна основной** \
Доменная логика гарантирует, что в рамках одного подразделения не будет двух записей `isPrimary = true`. Это правило живёт в домене, а не в контроллере или миграции.

### Сценарии использования такого домена в продукте

- **Создание новой АЗС**: менеджер создаёт подразделение «АЗС №13» внутри «Филиал Москва». Домен сам формирует `path = central-region/moscow-branch/station-13`, проверяет уникальность `slug` в пределах родителя и не даёт создать подразделение без валидного родителя или с некорректным именем.

- **Перевод бригады между станциями**: подразделение «Мобильная бригада №3» меняют с родителя «АЗС №12» на «АЗС №14». Домен пересчитывает `path`, проверяет отсутствие циклов и сохраняет новую иерархию. Фронтенд сразу видит обновлённое дерево без дополнительной логики.

- **Назначение ролей**: в «АЗС №12» добавляют должность «Оператор АЗС». Домен проверяет существование подразделения и должности, создаёт связь через `DepartmentPosition`. Если должность удалят, домен (или сервис агрегации) может запретить удаление, пока есть активные связи.

- **Поиск по ветке**: API запрашивает все подразделения с path LIKE `'central-region/moscow-branch/%'`. Это даёт всю ветку филиала за один запрос, а UI строит дерево, используя `path` как ключ иерархии.

- **Стабильные ссылки**: ссылка `/directory/central-region/moscow-branch/station-12` остаётся рабочей, даже если в будущем поменяют отображаемое название «АЗС №12» на «АЗС Flow‑12». `slug` и `path` остаются неизменными, а name можно менять свободно.
