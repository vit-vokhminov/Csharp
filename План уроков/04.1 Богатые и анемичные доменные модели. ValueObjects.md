# Богатые доменные модели и Value Objects

Продолжение [`clean-architecture-setup.md`](./clean-architecture-setup.md). К этому моменту у тебя
есть структура микросервиса: Domain, Core, Infrastructure, Web. Теперь разберём, как правильно
наполнять слой Domain — то есть как проектировать сущности и value objects.

**Цель:** понять, что такое богатая доменная модель, научиться выделять value objects и усвоить
принцип "никаких больших коллекций" — на реальном коде образовательной платформы.

---

## Что такое анемичная доменная модель

**Анемичная модель** (anemic domain model) — это класс, который хранит данные, но не содержит
поведения. Вся логика выносится в отдельные сервисы.

```csharp
// Анемичная модель — просто контейнер данных
public class IssueProgress
{
    public Guid Id { get; set; }
    public Guid IssueId { get; set; }
    public string Status { get; set; }
    public DateTime? StartedAt { get; set; }
}

// Логика живёт в сервисе
public class IssueProgressService
{
    public void StartWork(IssueProgress progress)
    {
        if (progress.Status != "NOT_STARTED") throw new Exception("...");
        progress.Status = "IN_PROGRESS";
        progress.StartedAt = DateTime.UtcNow;
    }
}
```

**Проблема:** логика размазана по нескольким сервисам. Ничто не мешает написать
`progress.Status = "COMPLETED"` прямо в коде без каких-либо проверок. Инварианты не защищены.

---

## Что такое богатая доменная модель

**Богатая доменная модель** (rich domain model) — это класс, который сам отвечает за свои
инварианты. Данные и поведение живут вместе.

**Инвариант** — правило, которое всегда должно выполняться для объекта. Например: "задача не
может перейти из COMPLETED в IN_PROGRESS напрямую". Богатая модель гарантирует соблюдение
инвариантов, анемичная — нет.

| Критерий | Анемичная модель | Богатая модель |
|----------|-----------------|----------------|
| Где живёт логика | В отдельных сервисах | В самом классе |
| Защита инвариантов | Нет гарантий | Нарушить невозможно |
| Создание объекта | `new Entity()` + ручная установка полей | Фабричный метод с валидацией |
| Изменение состояния | `entity.Status = "..."` из любого места | Только через методы класса |

---

## Что такое фабричный метод

**Фабричный метод** (factory method) — статический метод на классе, который создаёт объект
вместо конструктора. Возвращает либо готовый объект, либо ошибку.

```csharp
// Фабричный метод вместо public конструктора
public static Result<IssueProgress, Error> Create(Guid enrollmentId, Guid issueId)
{
    if (enrollmentId == Guid.Empty)
        return GeneralErrors.ValueIsInvalid(nameof(enrollmentId));

    return new IssueProgress(enrollmentId, issueId);
}
```

Почему не просто `public` конструктор? Конструктор не может вернуть ошибку — он либо создаёт
объект, либо бросает исключение. Фабричный метод возвращает `Result<T, Error>` и явно
сигнализирует: создание может не получиться. Подробнее про `Result` — в отдельном уроке.

## Шаг 1. Читаем богатую entity — IssueProgress

Открой файл `ProgressService/src/ProgressService.Domain/Issues/IssueProgress.cs`.
Это прогресс пользователя по задаче: в каком он статусе, когда начал, когда завершил.

### 1.1 Приватный конструктор + фабричный метод

```csharp
public sealed class IssueProgress : AggregateRoot
{
    private IssueProgress(Guid enrollmentId, Guid projectId, Guid issueId)
    {
        Id = Guid.CreateVersion7();
        EnrollmentId = enrollmentId;
        ProjectId = projectId;
        IssueId = issueId;
        Status = IssueProgressStatus.NOT_STARTED;
    }

    // Второй приватный конструктор — для Entity Framework
    private IssueProgress() { }

    public static Result<IssueProgress, Error> Create(Guid enrollmentId, Guid projectId, Guid issueId)
    {
        if (enrollmentId == Guid.Empty)
            return GeneralErrors.ValueIsInvalid(nameof(enrollmentId));

        if (projectId == Guid.Empty)
            return GeneralErrors.ValueIsInvalid(nameof(projectId));

        if (issueId == Guid.Empty)
            return GeneralErrors.ValueIsInvalid(nameof(issueId));

        return new IssueProgress(enrollmentId, projectId, issueId);
    }
```

**Что здесь происходит:**

- Конструктор `private` — создать объект через `new IssueProgress(...)` снаружи нельзя.
  Единственный способ — `IssueProgress.Create(...)`.
- `Create` возвращает `Result<IssueProgress, Error>`. Нет возможности получить объект
  без проверки его валидности.
- Начальный статус `NOT_STARTED` выставляется в конструкторе. Создать объект с другим
  начальным статусом физически невозможно.
- `Guid.CreateVersion7()` вместо `Guid.NewGuid()` — версия 7 содержит timestamp, что
  даёт монотонный порядок вставок в базу данных (лучше для индексов).

> ⚠️ **Важно:** второй пустой конструктор `private IssueProgress() {}` нужен Entity Framework
> для восстановления объекта из базы данных. Без него EF не сможет создать экземпляр при
> запросе. Он приватный — никакой бизнес-логики через него не прогнать.

### 1.2 Private setters

```csharp
public Guid Id { get; private set; }
public Guid EnrollmentId { get; private set; }
public Guid ProjectId { get; private set; }
public Guid IssueId { get; private set; }
public IssueProgressStatus Status { get; private set; }
public DateTime? StartedAt { get; private set; }
public DateTime? CompletedAt { get; private set; }
```

`private set` означает: прочитать поле можно снаружи, а записать — нет.
Никто не может написать `progress.Status = IssueProgressStatus.COMPLETED` в обработчике.
Изменить `Status` можно только через методы самого класса.

### 1.3 Методы с бизнес-логикой

Жизненный цикл задачи: `NOT_STARTED → IN_PROGRESS → UNDER_REVIEW → COMPLETED`.

```csharp
public UnitResult<Error> StartWork()
{
    if (Status == IssueProgressStatus.IN_PROGRESS)
        return UnitResult.Success<Error>(); // уже в нужном статусе — идемпотентно

    if (Status != IssueProgressStatus.NOT_STARTED)
        return ProgressErrors.InvalidStatusTransition(
            nameof(IssueProgress), Status.ToString(), nameof(StartWork));

    Status = IssueProgressStatus.IN_PROGRESS;
    StartedAt = DateTime.UtcNow;
    return UnitResult.Success<Error>();
}

public UnitResult<Error> SubmitForReview()
{
    if (Status != IssueProgressStatus.IN_PROGRESS &&
        Status != IssueProgressStatus.REQUESTED_CHANGES)
        return ProgressErrors.InvalidStatusTransition(...);

    Status = IssueProgressStatus.UNDER_REVIEW;
    StartedAt ??= DateTime.UtcNow; // заполняем если ещё не было
    return UnitResult.Success<Error>();
}

public UnitResult<Error> Approve()
{
    if (Status != IssueProgressStatus.UNDER_REVIEW)
        return ProgressErrors.InvalidStatusTransition(...);

    Status = IssueProgressStatus.COMPLETED;
    CompletedAt = DateTime.UtcNow;
    return UnitResult.Success<Error>();
}
```

**Что здесь важно:**

- Каждый метод сначала проверяет: можно ли сделать этот переход? Если нет — возвращает
  `Error`, не исключение.
- `StartWork` идемпотентен: вызвать его дважды подряд — не ошибка. Это защита от
  дублирующих запросов.

## Шаг 2. Читаем Value Objects

### Что такое value object

**Value object** — объект, который определяется своим значением, а не идентификатором.
Два `Price(100)` — это одно и то же, не важно, где они были созданы. Два `User` с одинаковыми
полями — всё равно разные пользователи, потому что у них разные ID.

**Главное свойство:** value object не имеет своего ID. Его "личность" — это его значение.

**Почему не просто примитив?** Примитив `decimal` не несёт смысла. `Price` говорит:
это цена, и у неё есть правила. Нельзя случайно передать отрицательную цену туда, где ожидается
цена — компилятор не даст.

### 2.1 Простой числовой VO — Price

```csharp
// EducationContentService.Domain/Courses/ValueObjects/Price.cs
public sealed record Price
{
    private Price(decimal value) => Value = value;

    public decimal Value { get; }

    public static Result<Price, Error> Create(decimal value)
    {
        if (value < 0)
            return GeneralErrors.ValueIsInvalid(nameof(value));

        return new Price(value);
    }
}
```

**Разбор:**
- `record` — C# автоматически генерирует `Equals`, `GetHashCode`, `==` по значению.
  `Price(100) == Price(100)` будет `true`. Для value objects это именно то, что нужно.
- `private Price(decimal value)` — нельзя создать Price без `Create`.
- Инвариант "цена не может быть отрицательной" выражен один раз и нарушить его невозможно.

### 2.2 Строковый VO с форматной валидацией — CourseSlug

```csharp
// EducationContentService.Domain/ValueObjects/CourseSlug.cs
public partial record CourseSlug
{
    public const int MIN_LENGTH = 2;
    public const int MAX_LENGTH = 100;

    private CourseSlug(string value) => Value = value;

    public string Value { get; }

    public static Result<CourseSlug, Error> Create(string value)
    {
        string normalized = value.Trim().ToLowerInvariant(); // нормализация

        if (normalized.Length < MIN_LENGTH || normalized.Length > MAX_LENGTH)
            return GeneralErrors.ValueIsInvalid(
                $"slug (от {MIN_LENGTH} до {MAX_LENGTH} символов)");

        if (!SlugPattern().IsMatch(normalized))
            return GeneralErrors.ValueIsInvalid(
                "slug (только строчные латинские буквы, цифры и дефисы, " +
                "не начинается и не заканчивается дефисом)");

        return new CourseSlug(normalized);
    }

    [GeneratedRegex(@"^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$")]
    private static partial Regex SlugPattern();
}
```

**Разбор:**
- `value.Trim().ToLowerInvariant()` — нормализация до вызова конструктора. Внутри объекта
  всегда будет уже чистое значение, не нужно нормализовать при каждом чтении.
- `[GeneratedRegex]` — атрибут, который просит компилятор сгенерировать regex один раз
  при старте приложения. Без него `new Regex(...)` компилировался бы при каждом вызове.
- `partial record` нужно, потому что `[GeneratedRegex]` генерирует код в отдельной части класса.
- Константы `MIN_LENGTH` / `MAX_LENGTH` используются и здесь, и в EF-конфигурации
  (`HasMaxLength(CourseSlug.MAX_LENGTH)`). Одно место правды.

### 2.3 Необязательный VO — Bio

```csharp
// AuthService.Domain/ValueObjects/Bio.cs
public record Bio
{
    public const int MAX_LENGTH = 1000;

    private Bio(string value) => Value = value;

    public string Value { get; }

    public static Result<Bio, Error> Create(string value)
    {
        string normalized = value.Trim();
        if (normalized.Length > MAX_LENGTH)
            return GeneralErrors.ValueIsInvalid($"bio (max {MAX_LENGTH} символов)");
        return new Bio(normalized);
    }

    public static Result<Bio?, Error> CreateOptional(string? raw)
    {
        if (string.IsNullOrWhiteSpace(raw))
            return (Bio?)null;  // пустое значение — не ошибка, просто null

        Result<Bio, Error> result = Create(raw);
        if (result.IsFailure)
            return result.Error;

        return result.Value;
    }
}
```

**Разбор:**
- `CreateOptional` — паттерн для необязательных полей. Пустая строка — не ошибка, просто
  отсутствие значения. В entity храним `Bio?`.
- Без `CreateOptional` пришлось бы писать эту логику в каждом обработчике, который
  принимает биографию.

### 2.4 Что делать VO, что не стоит

| Делать VO | Не делать VO |
|-----------|-------------|
| Есть ограничения: `Email`, `PhoneNumber`, `Price`, `Slug` | Простые поля без правил: `CreatedAt`, `UpdatedAt` |
| Есть нормализация: приведение к нижнему регистру, trim | Идентификаторы, если нет бизнес-смысла в ограничениях |
| Несколько связанных полей: `Address(city, street, zip)` | Флаги: `bool IsActive` — не нужна обёртка |
| Строгий формат: URL, координаты, цвет | |

**Общий принцип:** если у примитива есть правила или нормализация — выноси в VO.
Если примитив уже выражает всё, что нужно — не оборачивай.

## Шаг 3. Принцип — никаких больших коллекций на entity

### Проблема навигационных свойств

Представь такой класс:

```csharp
// Опасный паттерн
public class Course
{
    public List<Tag> Tags { get; set; }
    public List<Module> Modules { get; set; }
}
```

Когда Entity Framework загружает `Course`, он может автоматически (через `Include`) подгрузить
все теги и все модули. Если у курса 50 модулей и 30 тегов — запрос списка курсов потянет тысячи
строк из базы, хотя для отображения списка нужны только названия.

**Правило:** не ставить коллекции и навигационные объекты на доменные entity. Связи —
через ID. Если нужно загрузить связанные данные — делать это явно, отдельным запросом.

### 3.1 ID вместо объектов — CourseEnrollment

```csharp
// ProgressService.Domain/Enrollments/CourseEnrollment.cs
public sealed class CourseEnrollment : AggregateRoot, IOrderedItem
{
    public Guid UserId { get; private set; }    // не User
    public Guid CourseId { get; private set; }  // не Course
    public Guid AuthorId { get; private set; }  // не Author — денормализация
    public bool IsActive => ArchivedAt is null;

    public static Result<CourseEnrollment, Error> Create(
        Guid userId, Guid courseId, Guid authorId,
        EnrollmentSource source, SortKey sortKey, string? sourceRef = null)
    {
        // ...валидация...
        return new CourseEnrollment(userId, courseId, authorId, source, sourceRef, sortKey);
    }
}
```

`UserId`, `CourseId`, `AuthorId` — три простых `Guid`. Никаких навигационных свойств.
EF не подгрузит связанные объекты при запросе `CourseEnrollment`.

**Про `AuthorId`:** это денормализация. Когда строится лидерборд автора, нужно знать
чьи зачисления считать — не нужно идти за курсом ради одного поля `AuthorId`.
Это осознанный компромисс: избыточное хранение против дополнительного join.

### 3.2 Соединительная сущность вместо ICollection — EntityTag

Классическое решение для связи "много ко многим":

```csharp
// Так делать не нужно
public class Course
{
    public ICollection<Tag> Tags { get; set; } // EF создаст join-таблицу сам
}
```

Это создаёт неявную таблицу, и EF будет подгружать теги при любом `Include(x => x.Tags)`.

Вместо этого — явная соединительная сущность:

```csharp
// TagService.Domain/EntityTags/EntityTag.cs
public class EntityTag
{
    private EntityTag(EntityTagId id, TagEntityReference entityReference, TagId tagId)
    {
        Id = id;
        EntityReference = entityReference;
        TagId = tagId;  // Guid внутри, не объект Tag
    }

    private EntityTag() { } // для EF

    public EntityTagId Id { get; private set; }
    public TagEntityReference EntityReference { get; private set; }
    public TagId TagId { get; private set; }  // ID, не навигационное свойство

    public static Result<EntityTag, Error> Create(TagEntityReference entityReference, TagId tagId)
    {
        if (entityReference is null)
            return GeneralErrors.ValueIsRequired("entityTag.entityReference");

        return new EntityTag(EntityTagId.Create(), entityReference, tagId);
    }
}
```

`TagId` — это value object, внутри которого `Guid`. Объект `Tag` не загружается.
`EntityReference` — value object с типом и ID сущности (полиморфная ссылка: курс, модуль,
задача — всё через один тип).

Теги загружаются только когда они нужны — отдельным запросом через репозиторий или Dapper.

### 3.3 Ссылка на дочернюю сущность — Course.GettingStartedModuleId

```csharp
// EducationContentService.Domain/Courses/Course.cs
public sealed class Course : IOrderedItem
{
    public Guid AuthorId { get; }                        // не Author
    public Guid? GettingStartedModuleId { get; private set; }  // не Module

    public void SetGettingStartedModule(Guid? moduleId)
    {
        GettingStartedModuleId = moduleId;
        UpdatedAt = DateTime.UtcNow;
    }
}
```

Логически у курса есть "стартовый модуль". Но `Module` не загружается как объект автоматически.
Если нужна информация о модуле — делаешь отдельный запрос по `GettingStartedModuleId`.

### Итог по принципу

| Анти-паттерн | Правильный паттерн |
|-------------|-------------------|
| `List<Tag> Tags` на сущности | Явная соединительная сущность `EntityTag` |
| `public User User { get; set; }` | `public Guid UserId { get; private set; }` |
| `public Module GettingStartedModule { get; }` | `public Guid? GettingStartedModuleId { get; }` |
| EF сам управляет связями | Ты явно контролируешь, что загружается |

## Чеклист — применяешь ли ты эти принципы

Когда пишешь новую entity, проверь каждый пункт:

- [ ] Конструктор `private`. Создание только через `Create` или именованный конструктор
- [ ] `Create` возвращает `Result<T, Error>`, а не бросает исключение
- [ ] Все свойства с `private set` — изменения только через методы
- [ ] Каждый метод, меняющий состояние, проверяет инварианты и возвращает `UnitResult<Error>`
- [ ] Нет `public` полей или свойств с `public set`
- [ ] Value objects для всех концептуальных примитивов с правилами (Email, Slug, Price, ...)
- [ ] VO реализованы как `record` с приватным конструктором и `Result`-фабрикой
- [ ] Нет коллекций (`List<T>`, `ICollection<T>`) на entity для связей с другими агрегатами
- [ ] Связи между агрегатами — через ID (`Guid`)
- [ ] Связи "много ко многим" — через явную соединительная сущность

## Типичные ошибки

- **`public` конструктор без валидации** — любой может создать невалидный объект.
  Фикс: сделать конструктор `private`, добавить `Create`.

- **`public set` на свойствах** — кто угодно может сломать состояние.
  Фикс: `private set` везде, изменения только через методы.

- **`string Status` вместо enum** — компилятор не поймает опечатку `"COMPLTEED"`.
  Фикс: `enum IssueProgressStatus` с явными значениями.

- **VO без нормализации** — `CourseSlug("My Slug")` и `CourseSlug("my-slug")` это разные объекты.
  Фикс: нормализовать в `Create` до вызова конструктора.

- **Навигационное свойство `public Course Course { get; set; }`** — EF подгрузит курс при любом
  include. Фикс: оставить только `Guid CourseId`, убрать навигационное свойство.

- **Кидать исключение в методе entity** — метод `StartWork` не должен делать
  `throw new InvalidOperationException(...)`.
  Фикс: `return ProgressErrors.InvalidStatusTransition(...)`.
