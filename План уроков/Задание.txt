Нужно собрать первый use case для создания локации. Контроллер принимает HTTP-запрос, Application/Core проверяет входные данные и бизнес-правило, а репозиторий пока остаётся только контрактом. Реализация хранения появится позже. Result-подход, middleware для ошибок и нормальное HTTP-маппирование будут позже.

Бизнес-требование
Локации в системе должны иметь уникальные имена внутри компании. Иначе админ при выборе локации для подразделения не отличит один «Головной офис» от другого «Головного офиса».

Если на создание приходит уже занятое имя, операция должна отказаться с понятной ошибкой. Плюс нужна минимальная защита от мусора: имя и адрес не должны проходить в заведомо невалидном виде.

Что нужно сделать
Use case создания локации — добавь в Application/Core сценарий создания локации. Он принимает данные из API-контракта, проверяет их и возвращает id созданной локации.

Валидация запроса — проверь входные данные через FluentValidation: имя локации и поля адреса. На этом этапе невалидный ввод может приводить к исключению — Result-подход появится позже.

Контракт репозитория без реализации — в Application/Core нужен контракт для работы с локациями: добавить новую локацию и проверить, занято ли имя. Реализацию в инфраструктурном слое будет позже.

Бизнес-правило уникальности — перед созданием сценарий проверяет, свободно ли имя локации. Ошибка занятого имени должна отличаться от ошибки валидации формы, чтобы дальше её можно было корректно отдать клиенту.

Контроллер без заглушки — POST /locations должен делегировать работу в Application/Core, а не возвращать success-заглушку. Контроллер остаётся тонким: HTTP-контракт снаружи, бизнес-сценарий внутри.

Что должно быть готово
В Application/Core есть сценарий создания локации: принимает данные запроса, возвращает id созданной локации.
Валидация через FluentValidation проверяет имя локации и поля адреса; невалидный ввод не проходит дальше бизнес-сценария.
Контракт репозитория описывает добавление локации и проверку занятости имени; реализации пока нет.
Перед сохранением выполняется проверка уникальности имени; занятое имя даёт ошибку, отличимую от ошибки валидации.
POST /locations делегирует работу в Application/Core, а не возвращает заглушку.
