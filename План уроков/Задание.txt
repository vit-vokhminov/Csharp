Доменные модели не держат коллекции связанных сущностей внутри себя. Поэтому связь подразделения с локацией хранится отдельной сущностью DepartmentLocation, а Department не содержит список Location.

В этой задаче ты делаешь только создание подразделения. Обновление подразделения, обновление локации и отдельные операции привязки/отвязки локации будут в позже.

Бизнес-требование
Админ должен создать новое подразделение и сразу указать, на каких локациях оно работает. Если в запросе указана несуществующая локация или несуществующий родитель, операция должна отказаться целиком: в БД не появляется ни подразделение, ни связи.

Для дерева оргструктуры у подразделения должен быть стабильный path. Root-подразделение получает путь из собственного slug, дочернее — путь родителя плюс собственный slug. Это понадобится позже для быстрых запросов по дереву и UI.

slug здесь — не ещё одно отображаемое имя. Это стабильный технический сегмент подразделения: пользователь видит понятное название вроде «Отдел продаж», а система может использовать короткий код sales в ссылках, дереве и интеграциях. path — полный адрес узла в оргструктуре, поэтому его нельзя собирать случайно в каждом handler-е по-своему.

Что нужно сделать
Создание подразделения через API — POST /departments принимает name, slug, опциональный parentId и список locationIds. name — человеческое название для интерфейса, slug — стабильный код для пути и навигации. id нового подразделения генерируется на сервере, а не приходит из запроса.

Проверка родителя и локаций — если parentId указан, сервис должен найти родительское подразделение и взять его текущий path. Все locationIds должны существовать до сохранения нового подразделения.

Формирование доменной модели — Department создаётся через доменную фабрику или другой доменный способ, который проверяет name, slug, parentId и path. slug приходит отдельным полем, не автогенерируется из name, потому что переименование подразделения не должно автоматически ломать стабильный путь.

Стабильный path — склейка и проверка path живут в домене. Application/Core не должен собирать строку пути в разных местах по-разному. Тип path пока остаётся строкой; переход на PostgreSQL ltree будет slug.

Первичные связи с локациями — вместе с подразделением сохраняются записи DepartmentLocation для переданных locationIds. Если список пустой, подразделение создаётся без локаций.

Атомарное сохранение — создание подразделения и его первичных связей сохраняются как одна операция. Частичного состояния быть не должно.

Что должно быть готово
POST /departments с валидными name, slug, parentId и locationIds создаёт строку в departments и нужные строки в department_locations.
Если один из locationIds не существует, в БД не появляется ни новое подразделение, ни связь.
Если parentId не существует, значит это корень
Root-подразделение получает path, равный собственному slug; дочернее получает путь на основе path родителя и собственного slug.
Новый Department не принимает id из тела запроса; id генерируется на сервере.
В доменной модели Department нет коллекции связанных Location; связи представлены через DepartmentLocation и id сторон.
Ошибка сохранения логируется, но Result-подход и HTTP-маппинг в 4xx остаются для следующих задач.
В тексте/коде решения видно различие между name, slug и path: название показывается пользователю, slug служит стабильным сегментом, path отражает место в дереве.
